                   Self-Addressing IDentifier (SAID)
                        draft-ssmith-said-latest

Abstract

   A Self-Addressing IDentifier (SAID) is a content-addressable
   identifier that is cryptographically bound to a deterministic
   serialization and can be embedded within the structure it identifies.
   Embedding a preferred content address in the associated structure
   reduces ambiguity and supports interoperable, tamper-evident
   reasoning.  Derivation replaces the identifier field with a defined
   placeholder, deterministically serializes the structure, computes a
   cryptographic digest, and encodes that digest as the identifier.
   Verification repeats these steps, so any change to the serialization
   invalidates the identifier.

   Given sufficient cryptographic strength and successful verification
   under the identified derivation and serialization profile, a
   signature, digest, or another SAID that commits to a SAID also
   commits to the serialization identified by it.  Applications can
   therefore reference immutable data compactly by identifier rather
   than embedding the entire structure.  Examples include Verifiable
   Credentials, Ricardian Contracts, schemas, and other authenticatable
   data structures.

   Reproducibility depends on a deterministic wire-to-memory-to-wire
   round trip.  A receiver decodes bytes from a deterministic wire
   format into an in-memory value that preserves every serialization-
   relevant distinction; re-encoding under the same profile reproduces
   the identical byte sequence.  Ordered mappings, deterministic CBOR,
   and ASN.1 DER illustrate approaches that provide this stability.  The
   identifier representation also indicates or is associated with the
   digest algorithm, supporting cryptographic agility and future
   evolution.

   This document describes the native CESR realization and profiles
   comparable deterministic content-addressing and cryptographic-
   commitment properties for COSE/CBOR and JOSE/JSON.  The COSE
   realization uses an [RFC9995] hash envelope whose payload is the
   digest of deterministic CBOR data.  The JOSE realization omits the
   JWS payload and carries the digest in a critical protected-header
   parameter defined by the profile.  CDDL and JSON examples apply both
   envelope approaches to the same application structure.  These SAID-
   like constructions are distinguished from a natively self-referential
   SAID and require additional embedding and derivation rules to obtain
   self-reference.

1.  Introduction

   A content-addressable identifier is derived from the bytes of a
   serialization and is therefore cryptographically bound to those
   bytes.  This binding provides a root of trust for reasoning about the
   serialization: a sufficiently strong cryptographic commitment to the
   identifier is functionally equivalent to a commitment to the
   identified serialization.

   A self-addressing identifier (SAID) adds self-reference to content
   addressing by embedding the identifier within the serialization it
   identifies.  Directly hashing a serialization that already contains
   its own digest creates a circular dependency, so SAID derivation uses
   a defined placeholder for the identifier field.  The placeholder form
   is deterministically serialized and hashed, and the resulting encoded
   digest replaces the placeholder.

   A standard content address is computed from completed content and is
   normally maintained outside that content.  A SAID is instead both
   cryptographically bound to and carried within its serialization,
   making the preferred identifier self-contained.  The identifier
   representation also conveys or is associated with the digest
   algorithm used during derivation, enabling algorithm agility.

   An authenticatable data serialization is digitally signed so that a
   verifier can attribute it to the signer using the corresponding
   public key.  Such serializations often contain identifiers for
   themselves or references to other serializations.  If those
   identifiers are merely labels, an attacker can reuse the same label
   in altered content without detection.

   A SAID removes this ambiguity by binding the embedded identifier to
   the serialization that contains it.  Verification succeeds only when
   the serialization reproduces the bytes used during derivation; a
   mutation produces a different identifier.  References to other
   serializations by SAID therefore support compact, tamper-evident
   composition without embedding each referenced serialization in full.

   The urn said is now a registered namespace at IANA [URNSAID].  The
   urn said namespace uses the SAID protocol.

2.  Generation and Verification Protocols

   The self-addressing identifier (SAID) verification procedure follows
   these steps:

   *  Copy the embedded CESR [CESR] encoded SAID from the serialization.

   *  Replace the SAID field value with a placeholder of the same
      length.  The placeholder character is # (ASCII 35 decimal, 23
      hexadecimal).

   *  Compute the digest over the serialization containing the
      placeholder, using the digest algorithm identified by the copied
      SAID’s CESR derivation code.

   *  Encode the computed digest with CESR to produce a SAID having the
      same total length as the placeholder and copied SAID.

   *  Compare the copied SAID with the recomputed SAID.  Matching values
      indicate successful verification.

2.1.  Example Computation

   The CESR encoding of a Blake3-256 32-byte digest contains 44 Base64
   URL-safe characters.  The first character, E, identifies Blake3-256.
   A fixed-field serialization using that algorithm therefore reserves
   44 characters for the SAID.  Consider this initial serialization:

   field0______field1______________________________________field2______

   Replace field1 with 44 placeholder characters:

   field0______############################################field2______

   Computing Blake3-256 over the placeholder serialization and encoding
   the digest with CESR produces:

   E8wYuBjhslETYaLZcxMkWrhVbMcA8RS1pKYl7nJ77ntA

   Replacing the placeholder with that SAID produces the final
   serialization:

   field0______E8wYuBjhslETYaLZcxMkWrhVbMcA8RS1pKYl7nJ77ntA______

   Verification reverses these steps.

2.2.  Serialization Generation

2.2.1.  Deterministic In-Memory Representations

   The crucial consideration in SAID generation is reproducibility
   across the wire-to-memory-to-wire round trip.  The digest input is a
   byte sequence received from, or prepared for, a deterministic wire
   format.  Decoding those bytes produces an in-memory representation
   that retains every distinction needed to reconstruct the same
   serialization.

   A deterministic in-memory representation preserves field order when
   it affects the wire format, exact value types, numeric representation
   rules, string contents, optional-field presence, tags, and
   application normalization choices.  Re-encoding under the same
   deterministic profile produces identical bytes.  The digest covers
   those reproduced wire bytes, not an implementation-specific memory
   layout.

   Suitable realizations include an insertion-ordered mapping such as a
   Python 3.7 or later dictionary paired with a fixed JSON serialization
   profile, deterministic CBOR as described by [RFC8949], and ASN.1
   values encoded with DER under ITU-T [X690].  These are examples
   rather than prerequisites.  Any representation works when decoding
   preserves the information needed for deterministic re-encoding and
   independent implementations reproduce the same bytes.

   When mapping order affects the wire format, the in-memory
   representation preserves that order.  A profile can retain
   application-defined insertion order, sort keys, or apply schema-
   defined component ordering.  Encoders and decoders apply the selected
   rule consistently.

   Programming-language mappings have not always preserved insertion
   order.  If a native mapping lacks a stable ordering contract, an
   ordered mapping, schema-defined record, or explicit canonical sorting
   step establishes reproducibility.

2.3.  Example Ordered Mapping to JSON Serialization with SAID

   The following example uses a Python dictionary only as a concrete
   instance of a deterministic, insertion-ordered in-memory mapping.
   The same derivation applies to any representation that preserves the
   specified field order and value types:

   json {"said":"","first":"Sue","last":"Smith","role":"Founder"}

   Replace "said" with a 44-character placeholder and serialize without
   extra whitespace:

   json
   {"said":"############################################","first":"Sue","last":"Smith","role":"Founder"}

   Blake3-256 over those JSON bytes, encoded with CESR, produces
   EnKa0ALimLL8eQdZGzglJG_SxvncxkmvwFDhIyLFchUk.  Replacing the
   placeholder produces:

   json {"said":"EnKa0ALimLL8eQdZGzglJG_
   SxvncxkmvwFDhIyLFchUk","first":"Sue","last":"Smith","role":"Founder"}

   Verification restores the placeholder, reproduces the same JSON
   bytes, and recomputes the SAID.

2.4.  Example Schema Immutability Using JSON Schema with SAIDs

   A JSON Schema can use the same derivation procedure to give its "$id"
   field a self-referential, cryptographically bound identifier.  The
   placeholder serialization is:

   json
   {"$id":"############################################","$schema":"http://json-
   schema.org/draft-07/schema#","type":"object","properties":{"full_
   name":{"type":"string"}}}

   Digesting that serialization produces
   EZT9Idj7zLA0Ek6o8oevixdX20607CljNg4zrf_NQINY.  Replacing the
   placeholder yields:

   json {"$id":"EZT9Idj7zLA0Ek6o8oevixdX20607CljNg4zrf_
   NQINY","$schema":"http://json-schema.org/draft-07/
   schema#","type":"object","properties":{"full_
   name":{"type":"string"}}}

   Data structures using embedded SAIDs in this way are referred to as
   self-addressing data (SAD).

2.5.  Discussion

   A recognized derivation code identifies how to verify the binding
   between a SAID and its serialization.  A valid SAID confirms that the
   serialization reproduces the bytes used during derivation; a mutation
   produces a different identifier.  References to other serializations
   by SAID support compact, tamper-evident composition without embedding
   the referenced content in full.

3.  Realizing SAID-Like Properties with CESR, COSE, and JOSE

   The properties provided by a SAID can be realized through multiple
   representation and security frameworks.  Each realization requires a
   deterministic mapping from an application data model to bytes, an
   unambiguous indication of the digest algorithm and digest value, and
   verification rules that bind those bytes to the identifier.  The
   following subsections distinguish the native CESR construction from
   profiles based on COSE/CBOR and JOSE/JSON.

3.1.  CESR Realization

   The CESR realization defined by this document embeds the encoded
   digest in the serialization itself.  Its derivation code identifies
   the digest algorithm and encoding, while the dummy-value procedure
   resolves the otherwise circular dependency created by hashing content
   that contains its own identifier.  This construction is both content-
   addressing and self-referential: the identifier is a field of the
   exact serialization to which it is cryptographically bound.

3.2.  COSE/CBOR Realization

   [RFC9995] defines COSE hash envelopes by adding protected-header
   parameters that identify the payload hash algorithm, the media type
   or content format of the preimage, and optionally a location from
   which the preimage can be retrieved.  A SAID-like profile can use
   these parameters as follows:

   1.  Encode the application data using a specified deterministic CBOR
       profile consistent with Section 4.2 of [RFC8949].  The
       application profile needs to resolve every representation choice
       that could otherwise produce different byte strings for
       equivalent data.

   2.  Compute the selected cryptographic digest over those
       deterministic CBOR bytes.  The digest functions as the content-
       addressable identifier for that byte representation.

   3.  Construct an [RFC9995] hash envelope whose payload is the digest
       and whose protected header identifies the payload hash algorithm.
       The preimage content type and location parameters can be supplied
       when needed for interpretation or discovery.

   4.  Apply a COSE signature or MAC to the hash envelope.  A verifier
       can validate the COSE protection over the envelope and its digest
       without access to the detached preimage.  When the application
       data is available, the verifier deterministically encodes it
       under the same application profile, recomputes the digest, and
       compares the result with the envelope payload.

   This construction provides deterministic content addressing and a
   cryptographic commitment to detached content.  Unlike the CESR
   construction, it does not by itself make the digest a field of the
   hashed application structure.  It is therefore SAID-like rather than
   natively self-referential unless an application profile additionally
   defines an embedded digest field and a deterministic placeholder or
   exclusion rule.

3.2.1.  CDDL Example

   The ordered-mapping example in Section 2.3 can be represented as a
   deterministic CBOR map.  The following CDDL describes the application
   data before derivation, with the SAID field represented by the digest
   bytes that identify the deterministic encoding of the placeholder
   form:

   cddl said-example = { "said" => bstr .size 32, "first" => "Sue",
   "last" => "Smith", "role" => "Founder" }

   For derivation, the value of "said" is replaced by a 32-byte
   placeholder, and the resulting map is encoded using the selected
   deterministic CBOR profile.  SHA-256 over those bytes yields a
   32-byte digest.  The digest can then be carried as the [RFC9995]
   hash-envelope payload:

   cddl said-hash-envelope = #6.18([ protected : bstr .cbor { 1 => int,
   258 => int, 259 => "application/cbor" }, unprotected : {}, payload :
   bstr .size 32, signature : bstr ])

   Header parameter 1 identifies the COSE signature algorithm, parameter
   258 identifies the hash algorithm used to produce the payload, and
   parameter 259 identifies the preimage content type.  The payload is
   the digest of the deterministic CBOR encoding of the placeholder form
   of said-example.  Verification obtains the application data, restores
   the placeholder, deterministically re-encodes the map, recomputes the
   digest, and compares it with the envelope payload before or in
   conjunction with validating the COSE protection.

3.3.  JOSE/JSON Realization

   JOSE provides JSON-based signature and MAC containers through JWS as
   defined by [RFC7515].  Because JSON permits multiple textual
   representations of the same data model, a SAID-like JOSE profile
   first specifies an invariant byte representation.  [RFC8785] JSON
   Canonicalization Scheme (JCS) is one suitable profile: it constrains
   input to I-JSON, serializes primitives consistently, sorts object
   properties deterministically, and emits UTF-8.

   A JOSE realization can proceed as follows:

   1.  Canonicalize the application JSON using JCS or another explicitly
       identified deterministic JSON profile.

   2.  Compute a cryptographic digest over the resulting canonical UTF-8
       bytes and encode the digest using an unambiguous base64url
       representation.  The digest algorithm and canonicalization
       profile are fixed by the application profile or carried in
       protected parameters that verifiers are required to understand.

   3.  Place the base64url-encoded digest in a profiled protected-header
       parameter and list that parameter in "crit" so that a verifier
       recognizes the hash-envelope processing rules.  Omit the JWS
       payload from the JSON serialization.  The signature covers the
       protected header containing the digest; the detached application
       data is used only to recompute and compare that digest.

   4.  A verifier validates the JWS protected header and signature,
       obtains the application data separately, restores any defined
       placeholder, canonicalizes the JSON under the identified profile,
       recomputes the digest, and compares it with the digest carried in
       the protected header.

   JOSE does not currently register a general-purpose hash-envelope
   digest header equivalent to [RFC9995].  The example below therefore
   uses illustrative profiled parameter names.  A closed profile can
   define private names, while interoperable deployment calls for
   registered or collision-resistant names and explicit critical-
   parameter processing.  As with the COSE profile, the result provides
   deterministic content addressing and cryptographic commitment but
   becomes natively self-referential only when the application profile
   defines an embedded identifier field and placeholder or exclusion
   rule.

3.3.1.  JSON Example

   The application data is the same structure used in Section 2.3:

   json { "said": "", "first": "Sue", "last": "Smith", "role": "Founder"
   }

   After replacing "said" with the profile-defined placeholder, the
   structure is canonicalized with JCS and hashed with SHA-256.  The
   digest is base64url encoded and placed in the protected header.  The
   following flattened JWS JSON serialization illustrates the envelope
   before base64url encoding of the protected header:

   json { "protected": { "alg": "ES256", "crit": ["payload-digest",
   "payload-digest-alg", "payload-canonicalization"], "payload-digest":
   "<base64url(SHA-256(JCS(placeholder-form)))>", "payload-digest-alg":
   "sha-256", "payload-canonicalization": "jcs", "cty": "application/
   json" }, "signature": "<base64url(signature)>" }

   In an actual JWS JSON serialization, "protected" is the base64url
   encoding of the UTF-8 JSON protected-header object, not the object
   shown inline above.  The top-level "payload" member is absent.  A
   verifier decodes and validates the protected header, obtains the
   application data out of band, reconstructs the placeholder form,
   applies JCS, recomputes SHA-256, and compares the result with
   "payload-digest".  The names beginning with "payload-" are
   illustrative profile parameters and are not registered JOSE header
   parameters.

3.4.  Common Requirements and Distinctions

   All three realizations depend on collision-resistant digests,
   deterministic serialization, explicit algorithm identification, and
   exact verification rules.  CESR integrates these elements into an
   identifier designed for self-reference.  COSE with [RFC9995]
   standardizes a signed or MAC-protected hash envelope for CBOR-
   oriented systems.  JOSE can provide analogous behavior for JSON-
   oriented systems when combined with deterministic JSON
   canonicalization and a defined digest-envelope profile.
   Implementations do not treat semantic equivalence after parsing as
   sufficient; verification is performed over the exact deterministic
   byte representation prescribed by the applicable profile.

5.  Security Considerations

   Security depends on the collision resistance and second-preimage
   resistance of the selected digest algorithm and on consistent
   implementation of the applicable deterministic serialization profile.
   A verifier that uses different field ordering, type conversion,
   normalization, placeholder, or exclusion rules can compute a
   different digest from the producer.  Profiles therefore need to
   identify the digest algorithm, deterministic encoding rules,
   placeholder or exclusion procedure, and protected metadata needed to
   interpret the digest.  Implementations should reject unsupported
   algorithms and profiles, malformed or ambiguous serializations,
   duplicate map keys or object member names, and protected parameters
   they do not understand.  A valid digest demonstrates integrity of the
   identified bytes; it does not by itself establish authorship,
   authorization, freshness, confidentiality, or trustworthiness.  Those
   properties require the surrounding signature, MAC, key-management,
   and application trust model.

7.  Appendix: Embedding SAIDs in URLs

   A SAID can serve as a stable content identifier while discovery
   information is maintained separately.  An application can include the
   compact SAID in a protocol message or data structure, then use DNS-
   based discovery to locate a URI for a service or server from which
   the detached payload can be retrieved.  After retrieval, the
   application verifies the payload against the SAID.

   Separating integrity from discovery reduces message and data-
   structure size while retaining a cryptographic commitment to the
   referenced content.  The SAID identifies the content; DNS and the
   resolved URI identify a current retrieval location.  A change to that
   location for administrative reasons, such as a company domain-name
   change or service migration, does not alter the content bytes and
   therefore does not invalidate existing commitments to the SAID.

   The KERI community refers to this discovery pattern as an Out-of-Band
   Introduction (OOBI).  An OOBI associates a stable identifier with
   information that helps a client discover the current endpoint or
   resources needed to interact with the identified entity or retrieve
   identified content.
